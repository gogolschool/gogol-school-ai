# /newproduct

## Что делает

Переносит карточку продукта из таблицы Ноушн в OzmaDB (`crm.actions`): создаёт продукт, привязывает мастеров (`crm.masters_for_actions`), занятия, проставляет `price` / `split_parts`, обновляет поле «Ссылка в CRM» в карточке Ноушн. Поддерживает интенсивы, ISEEYOU, курсы, маркетинговые МК, открытые уроки (ОУ) и массовое создание за месяц.

## Как работает

1. **Загрузи актуальный мастер-промпт из Notion:** page `31f612c762af81ba999cc5657404528c`
   (https://www.notion.so/31f612c762af81ba999cc5657404528c). Действуй строго по нему — там маппинг полей, фиксированные справочники по типам, нумерация (`INT/ISEEYOU/OU/MK`), формат расписания, конвертация времени и самопроверка.
   > Notion берём через **рабочий** MCP (`c2755fd9-…`), не личный (см. память `feedback_notion_workspace_routing`).
2. Открой карточку(и) продукта по ссылке от пользователя, извлеки все поля.
3. Найди справочные ID в Озме (мастера, локация) — см. «Поиск ID» ниже.
4. **Покажи пользователю сводку** перед вставкой (имя/CODE, тип, даты, расписание, мастер, локация, цена, справочники) и дождись подтверждения — особенно при массовом создании.
5. Создай в Озме, обнови «Ссылка в CRM» в Ноушн, выполни самопроверку из промта, отчитайся ID и ссылками.

> Признаки АМК: в задаче перечень строк вида «1 мая (пт) 13-16», тип «МК по абонементу» / «АМК». Каждая строка с датой = отдельный продукт. ⚠️ У АМК мастера НЕ добавляются и занятия НЕ создаются (нет мастера → триггер занятий не сработает) — это нормально, так и задумано.
> Признаки «ссылки на оплату»: просят «ссылку на оплату», дают ID продукта из таблицы Notion. Это работа на **сайте (Bitrix)**, а не в Озме. Через API пишется всё, кроме **лимита мест** (Торговый каталог → «Доступное количество») — его проставляют вручную в админке, о чём предупреди пользователя. MAIN_SEVICE и PAYMENT_AVAILABLE **в услугах (iblock 16)** API пишет сам — проверено; запрет из [shared/CLAUDE.md](../../../../shared/CLAUDE.md#опасные-операции) на эти поля относится к расписанию (iblock 34), там по-прежнему только админка.
> Признаки «внутренней рассрочки»: просят «рассрочку от школы», «платежи 30/50/20», «три платежа по программе», «разбей ЛАБ-N на части». Это надстройка над ссылкой на оплату и работа только на **сайте (Bitrix)**, в Озме руками ничего не заводим — строку в [Рассрочках](https://ozma.gogol.school/views/crm/installments_table) создаёт автомат после оплаты первой части. ⚠️ Галочка «Внутренняя рассрочка» живёт только на трёх услугах-платежах, на основной услуге её быть не должно (см. правило 8).
> Признаки «расписания»: просят «добавь в расписание / на /schedule/», код длительной программы (LAB/INT/LCOURSE/PI/HEAD) и раздел сезона. ⚠️ `iblock_element_update` перезаписывает `detail_text` **целиком** — сперва `iblock_element_get` (element_id=27918, iblock_id=38), сохрани ВЕСЬ существующий HTML и добавь только новый `<li>`. Если текст подозрительно короткий (нет ожидаемых сезонных разделов) — **СТОП**, не записывай, предупреди о возможном раннем удалении. Ничего не удалять без явной команды.

## Критические правила (набиты практикой — в самом промте их нет)

### 1. Занятие создаёт триггер, не ты
Дочернее «Занятие» генерируется триггером `generate_lesson_after_master_adding` на `crm.masters_for_actions` — **при добавлении мастера**, а не при вставке продукта. Для одиночного однодневного продукта (даты `action_datetime` и `end_datetime` в один день) триггер создаёт ровно одно занятие сам.

**Поэтому порядок для одиночного МК/мероприятия:** (1) insert продукта → (2) insert мастера → занятие появится **само**. НЕ создавай занятие вручную — получится дубль, который придётся удалять. После — проверь:
`SELECT count(*) FROM crm.actions WHERE parent_action=<id> AND is_deleted=false` = ожидаемое число.
Для многодневных интенсивов генератор раскладывает занятия по дням недели из расписания — но всё равно сначала проверь, что натворил триггер, прежде чем досоздавать вручную.

### 2. Тип не из промта → уточняй у пользователя
Промт даёт фиксированные справочники для интенсивов, ISEEYOU и ОУ. Для **маркетинговых МК, курсов, мероприятий и прочего** значений нет. Не угадывай — найди в Озме 2–3 похожих продукта и предложи их конфиг, затем подтверди у пользователя `class_type`, `project`, `training_type`, `class_category`, `action_fin_project`, `fin_segment`.
Опорный конфиг **маркетингового МК** (Направление «Маркетинг»): `action_fin_project=36`, `project=1`, `class_category=9` (Другое), `fin_segment=1` (B2C), `class_type=2` (Мастер-класс) или `5` (Мероприятие), `training_type=5` (Творческий), `is_monitor_payments=false`.

### 3. Имя: код по промту vs описательное
Промт требует имя = CODE («Ссылка в CRM», напр. `MK01-202606`). Но команда иногда **вручную** переименовывает продукт в описательный формат «{Название для сайта} с {мастер в твор. падеже}» (напр. `veronikakorobova1` → «На языке дружбы с Александрой Сучковой»). Если в карточке «Ссылка в CRM» пустая и формат неочевиден — спроси пользователя, какое имя ставить. Кто и когда правил запись, видно через `query_events` (по `row_id`).

### 4. Время в UTC
OzmaDB хранит datetime в UTC. МСК = UTC+3 → перед записью **вычесть 3 часа** (`action_datetime`, `end_datetime`). Поля-даты `pl_start_date` / `pl_end_date` — без конвертации.

### 5. Подтверждение и идемпотентность
Перед вставкой — всегда сводка и подтверждение. Перед нумерацией — проверь занятые номера (`SELECT name FROM crm.actions WHERE name LIKE 'ПРЕФИКС%-ГГГГММ' AND type='Продукт'`). Не дублируй мастеров/заявки.

### 6. Мерч: без ответа «маркированный или нет» — не создавать
Мерч (`class_type`=10 «Товар») имеет обязательное поле **«Тип мерча»** `merch_kind` — enum `Мерч` / `Маркированный мерч` (одежда под «Честный ЗНАК»). Перед созданием **всегда** спроси у пользователя: «Это маркированный мерч или обычный?». **Без явного ответа создавать продукт запрещено** — не угадывать по названию, не ставить дефолт, не создавать «пока без типа». По маркированному мерчу в чек уходит код маркировки (`fin.transactions.mark_code`), и в списке транзакций подсвечиваются продажи мерча без отправленной маркировки — пустой `merch_kind` ломает эту сверку.

Если для мерча делается ссылка на оплату — в карточке платной услуги на сайте ставится галочка маркировки. ⚠️ Свойство ещё не выкачено с тестового (на 01.09.2026 в боевом iblock 16 его нет, скоро появится): проверь `iblock_fields(16)`, и если галочки нет — код свойства не выдумывай, услугу заведи без неё и предупреди пользователя, что галочку надо завести в админке Битрикса и проставить руками (создание свойств инфоблока через MCP недоступно). Полный конфиг мерча — в разделе «Мерч (товары)» мастер-промта.

### 7. Ссылка на оплату: три ловушки (детали — в мастер-промте)
Всё описано в промте «Создание ссылки на оплату на сайте» — здесь только маркеры, чтобы не проскочить мимо:

- **Цена — два поля.** Каталожная (`catalog_prices_set`) и свойство `PRICES` (ценовые пары). Рассрочку/Долями/Сплит включает флаг `CHECKED="2"` у действующей пары; при `"1"` они молча исчезают с формы, хотя цена показывается верно. Писать только `iblock_element_update` с обёрткой `{"VALUE": {…}}` — `services_update(prices=…)` затирает свойство.
- **Промокоды.** На пробных привязываются поимённо по ID (разделом не подтягиваются, от донора наследуется мусор); на длительных нужны разделы `64` + `56`.
- **Названия.** `NAME` и `PROPERTY_NAME` — CRM-код, `ADD_NAME` — человеческое название из «Темы» (`topic`) в Озме.

Самопроверка после создания — по промту: открыть страницу и убедиться, что `data-credit-full-price` ≠ 0 и в форме есть нужные способы оплаты.

### 8. Внутренняя рассрочка: галочка живёт только на услугах-платежах
Порядок целиком — в промте «Внутренняя рассрочка: как заводить программу и платежи». Здесь коды свойств iblock 16 и то, из-за чего рассрочка ломается молча:

- **Четыре услуги на одну программу:** основная (полная стоимость) + «платёж 1 из 3» 30 %, «платёж 2 из 3» 50 %, «платёж 3 из 3» 20 %. Имя платежа — `КОД-ПРОГРАММЫ_внутренняя рассрочка, платёж N из 3 (XX%)`. Эталон: `41459` (LAB01-2026H2, 98 000 ₽) → `42667` / `42668` / `42669`.
- **Свойства услуги-платежа:** `INTERNAL_INSTALLMENT="Y"`, `DENY_PROMOCODE="Y"`, `NIK_TG="Y"`, `PAYMENT_AVAILABLE=["cloud_pay_card"]` (только карта CloudPayments), `ADD_NAME="Внутренняя рассрочка"`, `NAME` — человеческий заголовок формы («ЛАБ-1 · платёж 1 из 3, 30% от стоимости»), `DATE_ACTIVE_TO` — как у основной услуги, цена одной парой `PRICES` без early birds и с `CHECKED="2"`.
- **Сертификат и бонусы — только на первом платеже:** `DENY_CERTIFICATE` / `DENY_BONUS_CARD` пустые у платежа 1 и `="Y"` у платежей 2 и 3. Второй и третий транши должны прийти деньгами.
- **Привязка на основной услуге:** `INSTALLMENT_PAY_1` / `_2` / `_3` = ID услуг-платежей. Первое обязательно — без него на странице программы не появится блок «Рассрочка от школы» с кнопкой «Оплатить первую часть»; второе и третье нужны, чтобы в CRM подтянулись суммы второго и третьего траншей.
- **⚠️ На основной услуге `INTERNAL_INSTALLMENT` НЕ ставим.** Иначе обычная оплата целиком (98 000 ₽) уедет в CRM как рассрочка и по ней автоматически заведётся лишняя строка с траншами. Галочка — только на трёх платежах.
- `INSTALLMENT_TERMS_URL` оставляем **пустым**: подставится https://gogolschool.ru/docs/pravila-vnutrenney-rassrochki/. Заполнять только под отдельные условия программы; выдуманный адрес = 404 в галочке согласия.
- Клон донора тянет за собой `PROMO_CODE` и `PROMO_CODE_SECTION` — на услуге-платеже это безвредно, потому что стоит `DENY_PROMOCODE="Y"`.
- Сетка 30/50/20 не произвольная: она равна модульной сетке **возвратов** из оферты (п. 5.9/5.10). Меняют оферту — рассрочку правим синхронно, иначе «оплачено» разъедется с «невозвратно» (память `reference_internal_installments`).

**Самопроверка (по промту):** на странице программы между блоком стоимости и формой появился блок «Рассрочка от школы» с разбивкой 30/50/20 → кнопка открывает попап «ВНУТРЕННЯЯ РАССРОЧКА» с суммой первого платежа → на втором шаге формы есть галочка «согласен с условиями «рассрочки»», ссылка в ней не даёт 404 → на странице оплаты **основной** услуги этой галочки нет.

## Поиск ID в Озме

- **Мастер:** ФИО в `base.people` (`first_name`, `last_name`). Но `crm.masters_for_actions.contact` ссылается на `base.contacts` (общий id с `base.people`). При нескольких тёзках бери того, кто реально используется мастером:
  `SELECT contact, count(*) FROM crm.masters_for_actions WHERE contact IN (...) GROUP BY contact`.
- **Локация:** `crm.locations` = тип площадки (1 Москва, 2 Выездной, 3 СПб, 4 Онлайн, 5 Региональный) — НЕ адрес. Конкретный адрес из «Место проведения» кладём в текстовое поле `street`.

## Формат транзакции

```json
{ "operations": [ { "type": "insert", "entity": {"schema": "crm", "name": "actions"}, "fields": { } } ] }
```
> `entity` всегда объект `{"schema":"…","name":"…"}`, не строка.
