# /check-economics — Егор Крид

Агент-эконом роли `doc-fin-ops`. Разбирает записи `fin.economics` с флагом-доп.комментарием и предлагает решения по P&L. Пара к `/bank`: `/bank` эти флаги СТАВИТ при внесении выписок, `/check-economics` их ЗАКРЫВАЕТ.

## Что делает

1. Собирает очередь записей `fin.economics`, где `additional_comment` непустой (флаги «требует проверки — …» от `/bank` и любые ручные пометки).
2. По каждой записи парсит намерение флага и дорасследует по фактам (текст платежа, справочники Озмы, правила разнесения): предлагает `project` / `expenditure_type` / `segment` / `marketing` / `referenced_employee` (мастер) / период (`start_date`/`end_date`) / `split_parts` (разбивка по проектам).
3. Считает **эффект на P&L**: итоговую категорию (`fin.pl_categories`), проект и месяц (`pl_date = start_date`) — показывает «было → станет».
4. После подтверждения человека вносит правку в Озму, гасит флаг и **проверяет, что строка `fin.pl_report_final` пересобралась** (см. ловушку триггера в мастер-промпте).

## Как работает

1. **Загрузи актуальный мастер-промпт из Notion:** page `3a7612c762af81e38ca7c55f09eefecb`
   (https://www.notion.so/3a7612c762af81e38ca7c55f09eefecb). Действуй строго по нему — там очередь-запрос, разбор по типам флагов, механика economics ↔ P&L, ловушка триггера пересборки, форматы сообщений для Telegram и правила эскалации.
   > Notion берём через **рабочий** MCP (`c2755fd9-…`), не личный (см. память `feedback_notion_workspace_routing`).
2. Мастер-промпт ссылается на канонические источники правил — тяни их живьём при классификации:
   - Правила разнесения по направлениям/проектам/статьям — `198612c762af80be89dbd507f53aa0fb`;
   - Правила автопроставления категории («Расходы по категории») — `197612c762af80379a4ede761e95cdbf`;
   - Проверки экономики и PL — `197612c762af804eab3ff23e4e8cb621`.
3. Собери очередь, покажи количество и группировку по типу флага (крупнейшие суммы вперёд).
4. По каждой записи — разбор, предложение с эффектом на P&L, вопрос **да / правка / пропустить**.
5. Только после «да» — запись одной транзакцией `mcp__ozma__transaction`, гашение флага, проверка `pl_report_final`. Отчёт: что разнесено, как обновилась строка P&L, сколько флагов осталось.

## Железные правила (кратко; полностью — в мастер-промпте)

- **Confirm-first на запись** в `fin.economics`/`fin.pl_report_final`. Ничего не писать без «да» (память `feedback_ozma_refunds`).
- **Не угадывать** проект/статью/сумму: неоднозначное, спорное, конфликтное, требующее встречи-сверки — эскалация Бэлле, кейс в «нужно решение».
- **Читать правила живьём** (ID проектов/статей/сегментов/категорий и правила разнесения меняются) — не хардкодить.
- **Идемпотентность**: перед правкой перечитать строку; уже разобранное (флаг снят / `is_transaction_checked=true`) не трогать.
- **Ловушка P&L-триггера**: `update_pl_after_amount_changing` реагирует на `amount` — правка одной классификации может не пересобрать строку P&L; после записи проверить `fin.pl_report_final` по `external_transaction` и при необходимости обновить/форсировать. `pl_date = start_date`.
- **Категория P&L** — производная (`getCategoryForPLTransaction`: `expenditure_type + segment + project + marketing`), на `economics` не хранится; задаём через эти поля.

## Что НЕ делает

- Не вносит банковскую выписку (это `/bank`).
- Не создаёт транзакции продаж/возвратов (это `/newcontract` / возвраты).
- Не решает спорные разнесения и «встречные» сверки (маркетинг, абонементы, касса) — только эскалация.
