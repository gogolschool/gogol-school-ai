# /bank

## Что делает

1. **Внесение выписки Точки**: берёт банковскую выписку Точки (CSV или текстом) и разносит строки в `fin.economics` OzmaDB: правильные категории, контрагенты, теги, пометка `notification_who = "Клодик"`.
2. **Внесение выписки Консоль.Про**: разносит ЗП мастеров и комиссии платформы со счёта Консоли (account_type=15). Это ОТДЕЛЬНАЯ выписка — из выписки Точки по Консоли берётся только пополнение номинального счёта (ТИП Д), сами ЗП и Роялти-2 оттуда НЕ вносятся.
3. **Проверка остатков эквайринга**: сводит дельты в `fin.report_fin_balances_new` (account_type=6) и находит причины расхождений (фантомы, дубли, неверные даты возмещения, дубли НДС, авансовый счёт, возврат не на тот счёт). Цель — дельта 0 каждый месяц.

## Как работает

1. Загружает актуальный мастер-промпт из Notion:
   - внесение выписки Точки → page `320612c762af81ceb53bcfc18fd27514`;
   - **внесение выписки Консоль.Про (ЗП + комиссии) → page `337612c762af81e9b319f18251848a12`**;
   - **проверка остатков эквайринга → page `380612c762af81c79499c5eb239c63ff`**.
   Какой промпт брать — определяй по источнику: выписка Точки / выписка Консоли / сверка остатков.
2. Если выписка ещё не приложена — просит её у пользователя (файл / текст / ссылка).
3. Действует строго по мастер-промпту. Перед массовой вставкой — показывает превью первых 3–5 строк на проверку.
4. После вставки — отчитывается: сколько записей внесено, какие категории, общие суммы.

## Важно

- Tinkoff-эквайринг: с **11.02.2026** банк пишет «в т.ч. НДС» → комиссия = **3 записи** (доход / зеркальный расход / полная комиссия с НДС внутри). Отдельную строку НДС НЕ заводить — это давало задвоение (исправлено). До 11.02 было «Ставка НДС» (НДС отдельно) — там 4 записи, легитимно. Детали — в мастер-промпте.
- **Счета CloudPayments**: продажи в рассрочку и по «Долями» регистрируются на счета «CloudPayments - Рассрочка» (тип **21**) и «CloudPayments - Долями» (тип **20**). Выплаты и комиссии из выписки класть туда же, НЕ на исторические типы 11 «Рассрочка» и 1 «Долями» — иначе по одному типу висит только расход, по другому только доход. Формулировки в выписке не различаются, ошибка повторяется — сверяться по счёту продажи клиента.
- Удаление записей: сначала чистить зависимости в `fin.pl_report_final` (и `subscription_info`/`requests_for_subscriptions` для доходных проводок), потом основную запись.
- При сверке остатков: дата дохода = дата **возмещения** (как в банке), реестр матчить по «Дате перечисления», не «операции».
- Консоль: комиссия «Роялти-2» = **1,83 % от выплаты** (1,5 % + НДС 22 %) — по комиссии восстанавливается сумма выплаты (`выплата = комиссия / 0.0183`), это быстрый способ найти невнесённую ЗП. Комиссия ЗЕРКАЛИТ статью/направление/проект ЗП человека и делится пропорционально разбивке ЗП по проектам; `start_date` = месяц, ЗА который работа. Не сваливать всё в 101 / проект 32. Ловушка — объединённые переводы: одним платежом может уходить ЗП нескольких людей.
- Реклама (exp_type 107): проект по умолчанию — **Маркетинг (36)**, НЕ Лаборатории. Записи всё равно помечаются `additional_comment = «требует проверки — указать корректный проект рекламы»`, а в отчёте отдельным блоком просим у пользователя проект по каждой строке либо выгрузку **реестра самозанятых и ИП** (колонка «Вид услуг»: «реклама ППВ», «Реклама Хэд», «реклама интенсива», «реклама курса», «реклама школы» = Маркетинг). При правке проекта задним числом не забыть поправить и `fin.pl_report_final` — триггер тянет P&L только за суммой.
- Периоды рекламы в P&L: расход ложится на период работы рекламы, не на месяц оплаты. Набор (GS Head и т.п.) → `pl_start_date`/`pl_end_date` продукта из `crm.actions`; интенсивы → месяцы проведения; рекламная подписка (Яндекс) → 90 дней от оплаты (3 месяца); разовый блогер без набора → без периода. При смене числа месяцев старые строки P&L удалить и пересобрать через `fin.add_transaction_to_pl_report_from_economics_report`.
- Не править вручную — править мастер-промпт в Notion, чтобы изменения попали ко всем.
