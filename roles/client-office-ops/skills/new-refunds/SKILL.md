# /new_refunds

Пакетная обработка новых возвратов: проверяем «Анкеты на возврат» с сайта за период, сопоставляем со строками в Notion-таблице возвратов, заполняем форму возврата в Ozma, обновляем статус в Notion.

## Контекст, который нужно подтянуть перед работой

Эти источники меняются — **всегда** читать актуальные перед задачей через `notion-fetch`:

- **Инструкция по форме возврата в CRM (механика)** — `366612c762af81888363cae38b6dc9ad`. Точное описание полей `crm.refund_requests`, какая кнопка какой шаблон, как пишутся реквизиты. Из неё берём, что в какое поле кладём.
- **Алгоритм возврата (бизнес-процесс)** — `29d612c762af80e784d1d10a3b30c669` (актуальная NEW версия) и `18eefb7838c64fa4b39be573a54704d6` (старая, на всякий случай).
- **Notion-таблица «Таблица возвратов»** — `03f3c1ed71b2462ebc69495b83353f4e` (data source `3d37e5a4-902d-4dd7-8f77-55d761fe42ba`).

## Входные данные

Команда принимает диапазон дат в свободной форме:

- `/new_refunds за прошлую неделю`
- `/new_refunds с 13.05.2026`
- `/new_refunds с 01.05.2026 по 15.05.2026`
- `/new_refunds за май`

Парсим в `date_from` / `date_to` (DD.MM.YYYY). Если конец не указан — `date_to = сегодня`.

## Режимы запуска

**Интерактивный** (человек попросил в чате или скилл запущен руками) — порядок как описан ниже в шагах: сводка на Шаге 3 и ожидание «да» полностью в силе.

**Автономный прогон** (автозапуск по расписанию, в промпте сказано «автозапуск» — ежедневно в 11:00 по будням, период = последние 7 дней):

- Шаг 3 (сводка + «внести?») и Шаг 5 (вопрос про статус Notion) **пропускаются** — по ✅-строкам действуем сразу.
- Автоматически обрабатываются **только ✅-строки**. ✅ = контакт найден однозначно, заявка одна и продукт сматчился, `crm.refund_requests` по ней нет, реквизиты прошли валидацию, `SERVICEOPT` прочитан и однозначно смапился в `cancellation_to` (включая ветвление «сервисов»), нет конфликта с `*DOP`, `total_service_amount > 0`, `cancel_type` известен из Notion.
- **Всё остальное (⚠️ / 🔁 / ❌) не трогаем** — ничего не пишем ни в Озму, ни в Notion, выносим в топик «Сводки» блоком «нужно решение» с указанием, чего не хватает.
- **Идемпотентность обязательна** — подтверждающего человека в петле нет, а окно в 7 дней намеренно перекрывается между прогонами. Перед каждой записью проверять, что уже сделано (`crm.refund_requests` по заявке, статус строки Notion). Делать только недостающее, дублей не плодить.
- Если обработанных и проблемных строк нет — в чат не писать, ответить `NOOP`.
- Терминальные статусы Notion не ставить никогда (правило и так действует, в автономном режиме — особенно).

## Шаги

### Шаг 1 — собрать новые анкеты с сайта и сопоставить с Notion

1. Запросить анкеты:
   ```
   mcp__gogol-school-site__forms_results(
     form_id=7,
     include_values=true,
     page_size=30,      # маленькими страницами, см. ниже
     page=1
   )
   ```
   ⚠️ **`date_from`/`date_to` этот эндпоинт игнорирует** (проверено 30.07.2026: запрос за 01–02.01.2020 вернул свежие анкеты за июль 2026 и полный `total`). Передавать их бессмысленно — **фильтровать период самому по полю `dateCreate`** (формат `DD.MM.YYYY HH:MM:SS`).

   ⚠️ **Не тянуть всё разом.** Выдача отсортирована по убыванию даты, поэтому нужный период всегда лежит в начале. Запрашивать страницами по 30 и **остановиться на первой странице, где `dateCreate` ушёл левее `date_from`** — остальное не читать. Ответ тяжёлый: 30 анкет с `include_values=true` ≈ 144 КБ, все 344 ≈ 1,5 МБ; `page_size=500` забивает контекст целиком (проверено на прогоне 30.07 — сессия распухла до 1,4 МБ ради окна в 7 дней).

   В каждой анкете значимые поля (по `sid`): `SERVISE` (продукт), `SURNAME`/`NAME`/`OTCHESTVO`, `EMAIL`, `PHONE`, `TELEGRAM`, `RS`/`KS`/`BICJAR`/`NAMEOFTHEBANK` (реквизиты), `PURPOSEOFPAYMENT` (для рассрочки), `REASON` (причина), `DATEBIRTH`, **`SERVICEOPT` (radio «на какую карту вернуть» — приходит, см. Шаг 4)**. Группа `*DOP` — данные получателя если возврат на другого человека.

2. Подтянуть Notion-таблицу:
   ```
   notion-fetch на collection://3d37e5a4-902d-4dd7-8f77-55d761fe42ba
   ```
   Берём строки без терминального статуса (всё что не `деньги возвращены`, не `передумал`, не `перевод в сертификат`).

3. **Сопоставление**: каждой анкете подобрать строку Notion по `Почта` (точное совпадение) → fallback на `ФИО` (нормализация: lowercase, без лишних пробелов). Если матча нет — это новая заявка, **создать строку в Notion** (Шаг 4 ниже).

### Шаг 2 — найти заявку студента в Ozma

Из анкеты у нас: `EMAIL`, `ФИО`, `SERVISE` (название продукта в свободной форме, типа «Лаборатория Маски»). Нужно найти `crm.actions_for_contacts`:

1. По `EMAIL` находим контакт — **через `base.communication_ways`** (`email_sys` у многих контактов пуст, проверено 06.07.2026):
   ```
   funql_query: SELECT cw.contact, cw.contact=>main_name AS name FROM base.communication_ways AS cw
   WHERE cw.type = 'Email' AND LOWER(cw.data) = '<email в lowercase>' AND NOT cw.is_deleted
   ```
   Если ноль — fallback `SELECT id, main_name FROM base.contacts WHERE LOWER(email_sys) = '<email>'`, затем поиск по `main_name LIKE '%<Фамилия>%<Имя>%'`.
   Если несколько — взять с непустым `email`/`phone`.

2. По контакту находим **активные** заявки (поле даты — `create_datetime`, поля `action_datetime` в заявках нет; `cancellation_status` — reference на `crm.cancellation_statuses`, сравнивать по `=>name`):
   ```
   funql_query: SELECT id, action=>name AS product, create_datetime, request_status=>name AS status, cancellation_status=>name AS cancel_st
   FROM crm.actions_for_contacts
   WHERE contact = <contact_id>
   AND request_status IN (6, 7, 11, 13, 15, 18)  -- обучается / прошёл / оплатил
   AND COALESCE(cancellation_status=>name, '') NOT IN ('Деньги возвращены', 'Перевод в сертификат')
   ORDER BY create_datetime DESC
   ```

3. Из полученных выбрать ту, у которой `action=>name` лучше всего матчится с `SERVISE` из анкеты (нормализуем: оба в lowercase, ищем по ключевым словам — название интенсива/лаборатории/курса, код продукта). Если матч однозначный — берём. Если несколько кандидатов — показать список и спросить.

4. Проверить, нет ли уже `crm.refund_requests` для этой заявки:
   ```
   SELECT id, cancel_type, cancel_request_date, refund_amount FROM crm.refund_requests WHERE request = <request_id>
   ```
   Если есть и заполнено — **не дублировать**, только сообщить пользователю.

### Шаг 3 — собрать сводку и спросить

Показать пользователю таблицу:

| # | Анкета | Дата | ФИО | Продукт | Notion-статус | Ozma заявка | Возврат в Ozma |
|---|---|---|---|---|---|---|---|
| 1 | #123 | 13.05.2026 | Иванова А.О. | LCOURSE01-202604 | написать | id=54982 | нет |
| 2 | #124 | 14.05.2026 | … | … | заполнена анкета на возврат | id=54920 | id=47 (черновик) |

Спросить:
> Внести в Ozma по всем X заявкам?

**«На какую карту возврат» (`cancellation_to`) берём из анкеты — поле `SERVICEOPT` приходит заполненным** (см. Шаг 4). В сводке показываем прочитанное значение, а не спрашиваем заново. Уточнять у оператора нужно только в двух случаях:

- студент выбрал «оплачивал(а) через сервисы …», а по `tks_terminal_key` исходной оплаты не удалось однозначно определить, какой именно сервис (Долями / Яндекс Сплит / Т-Банк);
- `SERVICEOPT` конфликтует с `*DOP`-полями (например, опция «на мою карту», но заполнен получатель Петров) — показать оба сигнала и спросить.

Если по конкретной строке проблемы (контакта нет, заявок несколько, продукт не сматчили) — выделить и предложить пользователю выбрать/уточнить.

### Шаг 4 — внести данные в Ozma (после подтверждения)

Для каждой строки **создать запись в `crm.refund_requests`** (если ещё нет) через `mcp__OzmaMCP__transaction` с операцией `insert`. Маппинг полей (из инструкции `366612c762af81888363cae38b6dc9ad`):

| Поле в `crm.refund_requests` | Источник | Замечания |
|---|---|---|
| `request` | id заявки из шага 2 | ref |
| `cancel_request_date` | дата отправки анкеты (`createdTime`) | ISO datetime |
| `cancel_type` | из Notion `Тип возврата`: `полный` → `Полный возврат`, `частичный` → `Частичный возврат` | если в Notion пусто — спросить |
| `cancellation_to` | **читаем `SERVICEOPT` из анкеты** по таблице маппинга ниже | спрашиваем только при неоднозначности «сервисов» или конфликте с `*DOP` |
| `total_service_amount` | посчитать как сумму оплат: `SELECT SUM(CASE WHEN from_our_organization THEN -amount ELSE amount END) FROM fin.transactions WHERE request = <request_id> AND tks_state IN ('CONFIRMED','AUTHORIZED','SIGNED') AND NOT is_deleted` | если есть бонусы — учесть отдельно |
| `refund_commission_pct` | 2.6 (default) | если из Notion `Размер комиссии` другой — переопределить |
| `refund_amount` | **не заполняем** на этом этапе — `auto_refund_amount` посчитается триггером | пользователь потом сверит и при необходимости перебьёт |
| `cancel_account` | если есть бан-счёт у контакта — триггер `auto_fill_refund_request` подставит сам. Если возврат за сертификат — найти `fin.accounts` контакта с `type='Сертификат'` и поставить туда. | |
| `refund_requisites` | склеить из анкеты: `Счет получателя: <RS>\nБИК: <BICJAR>\nБанк: <NAMEOFTHEBANK>\nКорр. счёт: <KS>` | если хотя бы одно поле пустое — пометить и сказать пользователю |
| `order_num` | из `PURPOSEOFPAYMENT` если рассрочка | |
| `cancel_purpose` | `PURPOSEOFPAYMENT` целиком если рассрочка | |
| `refund_reason` | смап `REASON` из анкеты на enum: `Болезнь`, `Травма`, `COVID`, `Нет времени`, `Переезд`, `Не нравится мастер`, `Семейные обстоятельства`, `Работа (командировка)`, `Конфликт`, `Отмена программы`, `Мы отказали`, `Другое` | |
| `refund_reason_commet` | свободный текст из анкеты | |

После вставки — сообщить пользователю:
> ✅ Создал N возвратов в Ozma:
> - [Иванова А. О. — refund_view_form?id=47](https://ozma.gogol.school/views/crm/refund_view_form?id=47)
> - …
>
> Пересчитать сумму возврата для каждого? Сейчас стоит `auto_refund_amount` — он считается с учётом модулей и комиссии. Если нужно перебить вручную — скажи по какому id.

Если возникают вопросы (нет паспорта в Ozma, неоднозначный продукт, странная сумма) — спрашивать по ходу, не блокировать всю пачку.

### Шаг 5 — обновить статус в Notion (после подтверждения)

Спросить:
> Обновляю статус в Notion на «подготовка заявления» и ставлю сегодняшнюю дату?

Если **да** — для каждой обработанной строки Notion:
```
notion-update-page командой update_properties:
  "Статус": "подготовка заявления"
  "date:Дата статуса:start": <ISO today>
```

Если пользователь говорит другой статус (например, «запросили доки», «деньги возвращены», «передумал») — поставить тот.

## Подводные камни

- **Анкета без оплаты на сайте** — иногда студент заполняет анкету, хотя оплачивал не через сайт (наличные / Т-банк рассрочка / др.). В Bitrix-заказах его не будет, но в Ozma `fin.transactions` запись есть. Поэтому источник правды для `request` — Ozma, а не Bitrix-заказы.
- **«Анкета на возврат» = клиент уже хочет вернуть деньги.** Это статус Notion `заполнена анкета на возврат`. После создания записи в Ozma пользователь обычно сразу хочет сменить на `подготовка заявления`.
- **Несколько активных заявок у контакта** — например, человек на двух интенсивах. Если `SERVISE` неоднозначен — спросить.
- **Получатель «другой»** — если в анкете заполнены поля `SURNAMEDOP`/`NAMEDOP`/`OTCHESTVODOP`/`DATEBIRTHDOP`, ставим `cancellation_to = На карту другого человека` и заполняем `cancel_person_last_name`/`first_name`/`patronymic` в `crm.refund_requests`.
- **Сертификатная анкета** — если в SERVISE упоминается «сертификат», ставим `cancel_account` на сертификатный счёт контакта (тип `Сертификат` в `fin.accounts`). Дальше юзер увидит кнопку «Заявление (Сертификат)».
- **Не дублировать!** Перед вставкой всегда проверять `SELECT id FROM crm.refund_requests WHERE request = <X>`. Если уже есть — обновляем существующую, а не создаём новую.
- **«Опции» (`SERVICEOPT`) читаются — починили.** Раньше radio/checkbox не приходили из эндпоинта `/ajax/api/forms/.../results`, и `cancellation_to` приходилось подтверждать у оператора по каждой строке. Проверено 30.07.2026: `SERVICEOPT` и `AGREE` заполнены во всех 344 анкетах формы (25.03.2024 → 29.07.2026). Берём значение из анкеты, оператора дёргаем только на неоднозначностях.
- **Фильтр по датам в `forms_results` не работает.** `date_from`/`date_to` эндпоинт молча игнорирует и отдаёт свежие записи за всю историю. Опасно именно молчаливостью: запрос «за прошлую неделю» вернёт что-то похожее на правду. Всегда резать период самому по `dateCreate`.

## Какие статусы в Notion есть (для шага 5)

`написать`, `запросили доки`, `заполнена анкета на возврат`, **`подготовка заявления`** (по умолчанию после внесения в Ozma), `заявление на согласовании`, `заявление согласовано`, `позвали/отправили на подпись`, `подписано. положили в папку Бэлле`, `деньги возвращены`, `перевод в сертификат`, `перевод на другого человека`, `передумал`, `возврат скидки`.

## Что НЕ делать

- Не создавать транзакции возврата (`fin.transactions`) — это делает скил `/refund` уже после подписания заявления.
- Не отправлять письма / Telegram — это руками или другим скилом.
- Не менять статус в Notion на терминальный (`деньги возвращены`) — это финальный шаг после фактической выплаты.
- Не править триггерные поля (`auto_refund_amount`, `refund_amount_text`) — посчитаются сами.

## Проверки и обработка ошибок

Прогоняй эти проверки строго в указанном порядке — не молча скипать, а явно сообщать пользователю что нашёл.

### Парсинг диапазона дат

- Поддерживаемые форматы: «за прошлую неделю», «за эту неделю», «вчера», «сегодня», «за май», «за май 2026», «с 13.05.2026», «с 13.05.2026 по 15.05.2026», «13.05.2026 – 20.05.2026», «последние 7 дней».
- Если год не указан в `с DD.MM` — берём текущий. Если получается дата в будущем — берём прошлый год.
- Ассерты:
  - `date_from <= date_to` (если нет — поменять местами и предупредить).
  - `date_to <= сегодня` (если нет — обрезать до сегодня).
  - `(date_to - date_from) <= 90 дней` — иначе спросить пользователя «уверен, что нужно X дней?» перед запросом.
- Не понимаешь дату — спрашиваешь, не угадываешь.

### Bitrix-форма

- Сначала найди форму по `sid='ANKETA'` (а не по числу 7). Если sid поменялся / нет — ошибка пользователю.
- Если `forms_results` вернул больше 200 — есть пагинация. Не игнорируй: запроси все страницы.
- **Период режь сам по `dateCreate`** — серверный фильтр `date_from`/`date_to` не работает (см. «Подводные камни»). После фильтрации явно скажи, сколько анкет попало в период из скольких полученных: «за 20–29.07 — 12 анкет из 344».
- Проверь, что `SERVICEOPT` непустой хотя бы у части анкет. Если пусто у **всех** — сериализацию radio на сайте снова сломали: не подставляй `cancellation_to` молча, переходи на фолбэк с подтверждением у оператора и скажи об этом пользователю.

### Валидация полей анкеты

Для каждой анкеты проверь:

| Поле | Проверка | Если не прошло |
|---|---|---|
| `EMAIL` | содержит `@` и `.` | помечаем «нет валидного email», в Notion-матче ищем только по ФИО |
| `RS` (счёт получателя) | ровно 20 цифр после `replace(' ', '')` | флагуем «реквизиты невалидны», предупреждаем пользователя |
| `BICJAR` (БИК) | ровно 9 цифр | то же |
| `KS` (корр. счёт) | ровно 20 цифр | то же |
| `NAMEOFTHEBANK` | непустое | то же |
| `SURNAME`/`NAME` | непустые | пропускаем эту анкету, репортим в общую сводку |
| `DATEBIRTH` | дата в формате DD.MM.YYYY | предупреждаем (для документа нужна) |

Если хоть одно поле невалидно — анкета НЕ блокируется, но в сводке таблица помечает её ⚠️, а пользователь решает, что делать.

### Сопоставление с Notion

- Матч по `Почта` — точное (после `LOWER` и `TRIM`).
- Если матч множественный (несколько строк Notion с одной почтой) — выбрать ту, у которой статус НЕ терминальный (`деньги возвращены`, `передумал`, `перевод в сертификат`) и `Дата статуса` ближе всего к дате анкеты.
- Если все матчи терминальные — это уже **обработанный возврат**, новую запись в Notion НЕ создавать, а помечать в сводке: «у этого человека уже был возврат — точно новый?».
- Если матча нет — fallback: матч по `ФИО` (lowercase, без лишних пробелов). Если и так нет — создаём новую строку Notion со статусом «заполнена анкета на возврат».

### Поиск контакта в Ozma

Порядок поиска:

1. `base.communication_ways WHERE type = 'Email' AND LOWER(data) = <email> AND NOT is_deleted` → берём контакт оттуда (основной путь: `email_sys` у многих пуст; enum типа — именно `'Email'` с заглавной).
2. Если ноль — точный матч `LOWER(base.contacts.email_sys) = <email>`.
3. Если ноль — поиск по `phone_sys` (нормализовать: только цифры, последние 10).
4. Если ноль — `base.people.full_person_name ILIKE '%<Фамилия>%<Имя>%'`.
5. Если **больше одного** контакта — НЕ выбираем автоматически, выдаём пользователю список с email/phone/main_name и просим выбрать.
6. Если **ноль** во всех попытках — пропускаем эту анкету, помечаем в сводке «контакт не найден, нужно создать вручную».

### Поиск заявки

Из найденного контакта:

```sql
SELECT id, action=>name as product, action=>class_type=>name as ctype,
       create_datetime, request_status=>name as rs, cancellation_status=>name as cs
FROM crm.actions_for_contacts
WHERE contact = <contact_id>
ORDER BY create_datetime DESC
LIMIT 20
```

Проверки:

- Если все заявки контакта имеют `cancellation_status` IN ('Деньги возвращены', 'Перевод в сертификат') — у клиента не было активной заявки на момент анкеты. Помечаем «активной заявки нет» и спрашиваем пользователя.
- Если есть заявка с `cancellation_status = 'Деньги возвращены'` И продукт матчится с `SERVISE` из анкеты — это **повторный запрос** на уже завершённый возврат. ⚠️ Жирная пометка в сводке, ничего не делать без подтверждения пользователя.
- Матч заявки с `SERVISE` из анкеты: нормализуем оба (lowercase, убираем «лаборатория»/«интенсив»/«курс»/«мастер-класс»), сравниваем по ключевым словам ИЛИ по коду программы (`LAB05-2026H1`, `INT03-202604` — выделяем регуляркой `[A-Z]+\d+-?\d*`).
- Если матч однозначный — берём. Если несколько кандидатов — список пользователю.
- Если matches нет — пропускаем, помечаем.

### Проверка дубликатов `crm.refund_requests`

Перед вставкой ВСЕГДА:

```sql
SELECT id, cancel_type, cancel_request_date, refund_amount, modules_status_text
FROM crm.refund_requests
WHERE request = <request_id>
ORDER BY cancel_request_date DESC
```

- Если есть запись с той же `cancel_request_date` (±3 дня) — **не дублировать**, в сводке «уже есть refund_request id=X».
- Если есть запись с другой датой (старая) и `cancel_type='Частичный возврат'` — допустимо создать новый (например, добор частичного). Уточняем у пользователя.
- Если есть запись и `cancel_type='Полный возврат'` — НЕ создаём новый, ругаемся.

### Расчёт `total_service_amount`

Корректный запрос (исключаем возвраты и негативные строки):

```sql
SELECT COALESCE(SUM(amount), 0) as total
FROM fin.transactions
WHERE request = <request_id>
  AND tks_state IN ('CONFIRMED','AUTHORIZED','SIGNED')
  AND NOT is_deleted
  AND NOT from_our_organization     -- исключаем исходящие
  AND linked_transaction IS NULL    -- исключаем возвраты (связаны с исходными)
  AND amount > 0
```

- Если `total = 0` — пометить «оплат не найдено, проверь вручную», не подставлять в `crm.refund_requests`.
- Сверять с Bitrix-заказом: `mcp__gogol-school-site__orders_get(user_id=<id из контакта>, ...)`. Если суммы расходятся больше чем на 1 ₽ — пометить ⚠️.

### Определение `cancellation_to`

**Первичный источник — `SERVICEOPT` из анкеты.** Radio приходит заполненным (проверено 30.07.2026 на всех 344 анкетах формы с марта 2024 — пропусков нет). Не угадывать по контексту, если поле есть.

Enum в Озме — ровно 6 значений, «На сертификат» среди них **нет** (сертификатный возврат — это `cancel_type='Сертификат'` + `cancel_account`, а не `cancellation_to`).

| `SERVICEOPT` в анкете | → `cancellation_to` |
|---|---|
| `вернуть на мою карту, которой я платил` | `На свою карту (которой платил)` |
| `вернуть на другую мою карту` | `На другую свою карту` |
| `вернуть на карту человека, который платил за меня` | `На карту другого человека` |
| `оплачивал(а) через сервисы «долями», «яндекс сплит» или в рассрочку` | ветвим по источнику оплаты, см. ниже |

Матчить по подстроке (`другую мою` / `который платил за меня` / `через сервисы`), а не по точному равенству — формулировки на сайте могут поправить.

**Ветвление «через сервисы»** — один вариант радио покрывает три разных сервиса, различаем по исходной оплате:

```sql
SELECT pay_type, tks_terminal_key, account_from=>type as src_acc_type
FROM fin.transactions
WHERE request = <request_id> AND NOT from_our_organization AND amount > 0
ORDER BY transaction_date DESC LIMIT 1
```

- `tks_terminal_key LIKE '%dolyami%'` или Bitrix `pay_system_id` для Долями → `Через сервис Долями`
- `tks_terminal_key LIKE '%split%'` → `Через сервис Яндекс Сплит`
- `tks_terminal_key LIKE '%credit%'` или `tinkoff_credit` → `Через рассрочку Т-Банка`
- Не определилось — спросить оператора, не угадывать (у трёх сервисов разный порядок возврата).

**Сверка с `*DOP`.** Опция и поля получателя расходятся: на 344 анкетах `SURNAMEDOP` заполнен у 6, опция «карта человека, который платил за меня» стоит у 5, пересечение — 3. Поэтому:

- Опция «человек, который платил за меня» есть, `*DOP` пустые → ставим `На карту другого человека`, но помечаем ⚠️: для заявления нужны ФИО и дата рождения получателя, их придётся запросить.
- `*DOP` заполнены, а опция другая → конфликт, показать оба значения и спросить оператора.
- Если получатель по `*DOP` — сам клиент (совпадает ФИО) → это `На другую свою карту`.

Если `SERVICEOPT` пустой (историческая анкета или починка на сайте отвалилась) — падать назад на прежнюю эвристику: `*DOP` заполнены → `На карту другого человека`; иначе смотреть `tks_terminal_key`; иначе `На свою карту (которой платил)` — и обязательно подтвердить у оператора.

### Сертификатный возврат

Если в `SERVISE` встречается слово «сертификат» (case-insensitive) **или** заявка по продукту с `class_type=>name = 'Сертификат'`:

1. Найти сертификатный счёт контакта:
   ```sql
   SELECT id, final_certificate_number, expire_date_cer, nominal
   FROM fin.accounts
   WHERE contact = <contact_id> AND type = 'Сертификат' AND NOT is_deleted
   ORDER BY issue_date_cer DESC
   ```
2. Если ровно один — ставим в `cancel_account`.
3. Если несколько — список пользователю.
4. Если ноль — помечаем «сертификат не найден на контакте», спрашиваем.

### Маппинг типа возврата из Notion → Ozma

| Notion `Тип возврата` | Ozma `cancel_type` |
|---|---|
| `полный` | `Полный возврат` |
| `частичный` | `Частичный возврат` |
| (пусто) | спросить пользователя |

Если в Notion-строке `Возврат за:` = `сертификат` И Notion `Тип возврата` = `полный` → возможно правильнее `cancel_type='Сертификат'`. Уточнить.

### Маппинг `refund_commission_pct` из Notion

| Notion `Размер комиссии` | Ozma `refund_commission_pct` | `late_cancel_deduction_pct` |
|---|---|---|
| `2.6%` | 2.6 | NULL |
| `7% + 2.6% (>7 дней до начала)` | 2.6 | 7 |
| `2.2%` (старая) | 2.2 | NULL |
| `20% (при рассрочке)` | 0 | 20 |
| `20 + 2.2%` | 2.2 | 20 |
| `-` или пусто | 2.6 (default) | NULL |

### Обновление статуса в Notion

- Никогда не ставить терминальный статус: `деньги возвращены`, `передумал`, `перевод в сертификат`, `перевод на другого человека`, `подписано. положили в папку Бэлле`.
- Если у строки уже `подготовка заявления` или дальше по pipeline — НЕ перезаписывать, только обновить `Дата статуса` если пользователь явно попросил.
- Если строки в Notion НЕТ — создать со статусом `заполнена анкета на возврат`, ФИО, Почта, продукт из анкеты, тип возврата (если ясен), сегодняшняя дата.
