# Лана: ежедневная проверка «Шаблон рассылки» / «Расписание» перед стартом продукта

Дата: 2026-08-25

## Проблема

Продукты (наборы) стартуют без заполненного поля «Шаблон рассылки» (`crm.actions.template_newsletter`) — из-за этого рассылка перед началом занятий может не уйти вовсе. Аналогично для многозанятийных продуктов иногда не заполнено поле «Расписание» (`crm.actions.schedule_text`), которое тоже используется в рассылке.

Сейчас это никто не отслеживает системно — только если кто-то вручную заметит.

## Решение

Лана (бот `@gs_refund_bot` на ozma, systemd `lana-bot`) раз в день проверяет предстоящие продукты и, если что-то не заполнено, пингует Свету в специально созданном топике чата «NEW GS Возвраты».

### Кого и где проверяем

Базовый фильтр по продуктам — таблица `crm.actions`:
- `type = 'Продукт'`
- `is_deleted = false`
- `class_status` ∈ {`Запланировано` (id 1), `Согласовано` (id 2)} — активные, не отменённые и не уже проведённые
- `is_b2b IS NULL OR is_b2b = false` — **B2B-продукты исключены** (решение от 25.08.2026, пересматривает первоначальный вариант «проверять всё»): у B2B нет единой рассылки студентам, поле `template_newsletter` для них системно нерелевантно
- `class_type IS NULL OR class_type <> 18` — **МК по абонементу (АМК) исключены** (решение Бэллы от 27.08.2026): по абонементам рассылка через это поле не идёт вовсе — в `crm.send_reminders_for_product` тип 18 не входит в `CLASS_TYPES_TO_SEND`, так что при пустом `template_newsletter` функция выходит молча. Напоминания об оплате по абонементам админы шлют отдельно, по Notion-таблице регулярных рассылок (скилл `/rassylki`). Фактически поле у АМК не заполняют никогда (141 продукт за 2026 — 0 заполненных), поэтому чек давал только ложные срабатывания. Форма `class_type IS NULL OR …` — чтобы продукты без указанного типа из проверки не выпадали
- `action_datetime` (дата и время первого занятия, хранится в UTC) в окне `[сегодня 00:00 МСК; сегодня+4 00:00 МСК)` — старт сегодня или в ближайшие 3 дня. **Не `pl_start_date`** (исправление Бэллы от 06.09.2026, первоначально фильтр был по нему): `pl_start_date`/`pl_end_date` — это период признания выручки в P&L (по нему считается `total_month_count`), и у открытых уроков там стоят даты лаборатории, к которой ведёт ОУ, а не дата самого урока. Из-за этого чек молчал по OU02/OU03/OU04-202609 (старт 06.09, `pl_start_date` 13–17.09). У части продуктов `pl_start_date` вовсе пустой (например INACHE03) — такие из проверки выпадали целиком

Внутри оставшихся (не-B2B, не-АМК) продуктов исключений по типам нет — поле «Шаблон рассылки» имеет валидное значение «Не высылать» (id 12 в `crm.newsletter_templates`), которым можно осознанно закрыть отдельный продукт, для которого рассылка не нужна. Тип целиком выносим в фильтр только тогда, когда поле для него системно нерелевантно (B2B, АМК), — иначе пришлось бы вручную ставить «Не высылать» на каждый новый продукт этого типа.

### Чек 1 — шаблон рассылки

Из отфильтрованных продуктов — те, где `template_newsletter IS NULL`.

Пример FunQL:
```sql
SELECT id, name, action_datetime, template_newsletter
FROM crm.actions
WHERE type = 'Продукт'
  AND is_deleted = false
  AND class_status IN (1, 2)
  AND (is_b2b IS NULL OR is_b2b = false)
  AND (class_type IS NULL OR class_type <> 18)
  AND action_datetime >= '<сегодня>T00:00:00+03:00'::datetime
  AND action_datetime < '<сегодня+4>T00:00:00+03:00'::datetime
  AND template_newsletter IS NULL
ORDER BY action_datetime
```

### Чек 2 — расписание

Из отфильтрованных продуктов — те, где `schedule_text IS NULL` **и** у продукта больше одного дочернего занятия:
```sql
SELECT a.id, a.name, a.action_datetime, a.schedule_text,
  (SELECT count(*) FROM crm.actions AS l
   WHERE l.parent_action = a.id AND l.type = 'Занятие' AND l.is_deleted = false) AS lesson_count
FROM crm.actions AS a
WHERE a.type = 'Продукт'
  AND a.is_deleted = false
  AND a.class_status IN (1, 2)
  AND (a.is_b2b IS NULL OR a.is_b2b = false)
  AND (a.class_type IS NULL OR a.class_type <> 18)
  AND a.action_datetime >= '<сегодня>T00:00:00+03:00'::datetime
  AND a.action_datetime < '<сегодня+4>T00:00:00+03:00'::datetime
  AND a.schedule_text IS NULL
```
затем в коде отфильтровать `lesson_count > 1` (однозанятийные МК/ОУ не нуждаются в тексте расписания).

### Повтор и снятие с контроля

Никакого дедупа/памяти об уже отправленных напоминаниях не ведётся: проверка идёт каждый день заново, и пока поле пустое — продукт попадает в список снова. Как только поле заполнено любым значением (включая «Не высылать») — продукт перестаёт попадать в выборку.

Топик: `https://t.me/c/3933036305/988` → чат `-1003933036305` («NEW GS Возвраты»), thread_id `988`.

Если чек 1 непуст — отдельное сообщение:
```

— <Название продукта> (старт <ДД.ММ.ГГГГ>) — https://ozma.gogol.school/views/crm/class_form?id=<id>

```

Если чек 2 непуст — отдельное сообщение (то же оформление, другой заголовок):
```
@Beverkar2 НЕ ЗАПОЛНЕНО РАСПИСАНИЕ ДЛЯ РАССЫЛКИ

— <Название продукта> (старт <ДД.ММ.ГГГГ>) — https://ozma.gogol.school/views/crm/class_form?id=<id>
— …
```

Дата в скобках «старт …» — `action_datetime` в московском времени (+3 часа к UTC). Оба чека — из одного прогона Ланы, но два разных блока текста, разделённых строкой `---` (существующий у Ланы механизм: `respond()` шлёт такие блоки отдельными сообщениями с паузой 1.2с). Если один из чеков пуст, соответствующий блок не выводится вовсе (не слать пустых сообщений). Если пусты оба — в чат ничего не уходит (тишина, как у остальных плановых прогонов при отсутствии находок).

### Где живёт логика

**Новый скилл** в репозитории (git-клон на сервере в `/home/agentbot/gogol-school-ai`, пуллится после `git push`):
`roles/client-office-ops/skills/check-newsletter-templates/SKILL.md`

Скилл делает оба FunQL-запроса через Ozma MCP и формирует итоговый текст по описанному выше формату (или пустой ответ/NOOP, если оба чека пустые).

**Новая job в `bot.py`** (`/home/agentbot/bots/lana/bot.py`, systemd `lana-bot`), по образцу существующих плановых прогонов (анкеты 11:00 будни, сводка 12:00 будни):
- Env `ORCH_NEWSLETTER_HOUR = 10`
- Запускается **каждый день, включая выходные** (в отличие от анкет/сводки, которые только по будням)
- Прогон **не silent** — итоговый текст модели уходит напрямую в топик `988` того же чата `-1003933036305` (не в топик 3 «Сводки»)
- Анти-повтор в рамках суток — через существующий `state.json["sched"]`, как у других job
- Тест при старте: `ORCH_RUN_ON_START=newsletter` (по аналогии с `mail`/`digest`)

**PERSONA** в `bot.py` не трогаем: «Железное правило №2» ограничивает автономные ЗАПИСИ в CRM/Notion, а новая job только читает Ozma и шлёт сообщение — как уже делает `digest`, которая тоже не упомянута в правиле №2 и работает без правок PERSONA.

Отдельный skill-файл в репозитории (как планировалось изначально) тоже не создаём: у job `digest` бизнес-логика зашита прямо в промпт `bot.py`, без отдельного скилла — новая job следует тому же паттерну (см. план реализации).

### Тестирование перед боевым включением

1. Бэкап `bot.py` (`bot.py.bak-20260825` по существующей конвенции).
2. `python3 -m py_compile bot.py` — синтаксис ок.
3. Ручной прогон: `systemctl stop lana-bot`, затем `sudo -u agentbot ORCH_RUN_ON_START=newsletter timeout 300 python3 bot.py` — проверить, что сообщение(я) реально приходят в топик 988 в ожидаемом формате (или тишина, если сейчас нечего слать — судя по разведке 25.08.2026, в окне уже есть кандидаты без обоих полей, так что прогон должен что-то прислать).
4. `systemctl start lana-bot`, проверить `systemctl is-active` и `journalctl -u lana-bot -n 20`.

## Вне охвата

- Не проверяем прошедшие/отменённые продукты.
- B2B-продукты и МК по абонементу исключены целиком (см. фильтры `is_b2b` и `class_type`); внутри оставшихся типов различий нет — см. решение про «Не высылать».
- Не ведём отдельного учёта «уже напоминали» — простое ежедневное перевычисление.
- Не трогаем существующие job (почта, анкеты, сводка) — новая job независима.
