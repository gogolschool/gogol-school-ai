# B2B CRM в Озме — дизайн

**Дата:** 03.09.2026
**Источник ТЗ:** Notion «ТЗ для озмы (система В2В)» — https://app.notion.com/p/3ce612c762af80e48f0fc5aaf5d22d33
**Статус:** согласовано устно, ждёт вычитки

## 1. Задача

Сейчас в Озме есть только **продукт B2B** (`crm.actions` с `is_b2b = true`, 20 записей) и договор к нему. Нет истории отношений с клиентом и нет процесса продажи: контакт клиента хранится тремя текстовыми полями, неуспешные запросы не фиксируются нигде, вернуться к клиенту через год не по чему.

Строим два новых слоя поверх готового продукта — **Клиент** и **Сделка** — по принципу из ТЗ:

- **Сделка** отвечает «как мы продавали»;
- **Продукт** — «что в итоге купил клиент»;
- **Клиент** — «какие у нас отношения и что произошло за всю историю».

Продукт не переделываем: добавляем в него поля и связь со сделкой.

## 2. Принятые решения

| Вопрос | Решение |
|---|---|
| Компания как отдельный уровень | **Не заводим.** Клиент — верхний уровень. «Компания» = организация (`base.organizations`), привязывается к клиенту связью M:N |
| Кто заполняет организацию | Менеджер по документообороту (договорённостью, не ролями) |
| Охват внутри компании | Группировка клиентов по привязанной организации — закрывает комментарий к ТЗ «сколько клиентов в одной компании охватываем» |
| Статус vs действия | **Два разных объекта.** Статус — одно поле на сделке, история его смен пишется автоматически в лог. Действия — отдельный список задач со сроком, из них идут напоминания |
| Сделка → продукт | **1:N**, из одной сделки может родиться несколько продуктов |
| Сумма на сделке | Есть — ожидаемая сумма, плюс расчётная фактическая (сумма цен продуктов) |
| Финальный успешный статус сделки | **«Продано»** (договорились и подписали). «Программа проведена» — это статус продукта, а не сделки: продуктов у сделки может быть несколько и проводятся они в разное время |
| Яндекс.Диск | Папка сделки создаётся автоматически самой Озмой |
| Напоминания | Не делаем внутри Озмы. Готовим данные и точки подключения для отдельного Telegram-агента |
| Роли и права | Не разграничиваем |
| Миграция истории | Отдельным этапом после того, как структура заработает |

## 3. Модель данных

### 3.1 Клиент

**`crm.b2b_clients`** — верхний уровень. Клиент может быть компанией целиком (Mindbox) или подразделением (Сбер-образование, Сбер-риски — два разных клиента).

| Поле | Тип | Назначение |
|---|---|---|
| `name` | string, not null | «Сбер-образование», «Яндекс — топ-перформеры» |
| `team` | string | команда / подразделение, если не вошло в название |
| `account_manager` | ref → `base.people` | ответственный аккаунт с нашей стороны |
| `budgeting_month` | int (1–12) | месяц начала бюджетирования — основа для проактивного напоминания |
| `budgeting_note` | string | детали цикла согласования бюджета |
| `next_contact_date` | date | дата следующего контакта |
| `next_contact_reason` | string | повод для возвращения |
| `next_offer` | string | потенциальное следующее предложение |
| `disk_folder` | string | ссылка на папку клиента на Яндекс.Диске |
| `notes` | string | |
| `is_deleted` | bool | |

Счётчики (сделок, выигранных сделок, продуктов) и дата последнего контакта считаются во вью подзапросами, а не вычисляемыми полями: OzmaDB не разрешает подзапрос в выражении вычисляемого поля. Вычисляемое поле на самой таблице одно — `main_name` («Клиент — Команда»).

**`crm.b2b_client_organizations`** — связь M:N клиента и юрлиц: `client`, `organization` (→ `base.organizations`), `is_primary`, уникальность по паре.

Почему M:N, а не одно поле: одно подразделение в разные годы платит через разные юрлица или через агентство. Одно поле заставило бы плодить клиентов при смене плательщика и разрывало бы историю отношений.

**`crm.b2b_client_contacts`** — люди внутри клиента: `client`, `full_name`, `position`, `department`, `telegram`, `email`, `phone`, `person` (опциональная ссылка на `base.people`), `is_primary`, `notes`.

### 3.2 Сделка

**`crm.b2b_deals`**

| Поле | Тип | Назначение |
|---|---|---|
| `client` | ref → `crm.b2b_clients`, not null | |
| `name` | string | краткое название сделки |
| `source` | ref → `crm.b2b_deal_sources` | канал, откуда пришёл запрос |
| `source_person` | ref → `base.people` | конкретный человек, если известен (в т.ч. из базы B2C-студентов) |
| `client_request` | string (длинный) | **первоначальный запрос дословно, языком клиента** — чтобы в продажах говорить его словами |
| `our_understanding_note` | string | свой вариант понимания запроса, если не подошёл ни один из справочника |
| `status` | ref → `crm.b2b_deal_statuses` | |
| `amount` | decimal | ожидаемая сумма |
| `organization` | ref → `base.organizations` | юрлицо-заказчик, выбор ограничен привязанными к клиенту |
| `audience` | enum | топ-команда / линейные сотрудники / смешанная команда |
| `loss_reason` | ref → `crm.b2b_loss_reasons` | обязательно при закрытии в неуспех |
| `materials_link` | string | ссылка на материалы (зум, расшифровка, интервью) |
| `disk_folder` | string | ссылка на папку сделки на Диске |
| `disk_folder_status` | enum | нет / создаётся / создана / ошибка |
| `tg_topic_id` | string | топик в Telegram-чате под эту сделку — для будущего агента |
| `responsible` | ref → `base.people` | по умолчанию наследуется от клиента |
| `closed_date` | date | |
| `notes`, `is_deleted` | | |

Вычисляемое поле одно — `main_name`. Последнее действие и число продуктов считаются во вью (см. выше про подзапросы).

**`crm.b2b_deal_directions`** — связь M:N сделки и направлений: наше понимание запроса, мультивыбор. В Озме мультивыбор реализуется отдельной таблицей связей, одним полем не обойтись.

### 3.3 История статусов и действия

**`crm.b2b_deal_status_log`** — пишется триггером, руками не заполняется: `deal`, `status_from`, `status_to`, `changed_at`, `changed_by`, `comment`.

**`crm.b2b_deal_actions`** — задачи и контакты по сделке, источник напоминаний: `deal`, `type` (→ `crm.b2b_action_types`), `action_datetime`, `status` (Запланировано / Выполнено / Отменено), `responsible`, `comment` (что сделать), `result` (что вышло).

Интерфейс отметки простой: действие фиксируется кликом, дата ставится текущая, её можно изменить задним числом.

**Отдельно оговорено:** не повторяем ловушку `sales.actions`, где триггер просрочки автоматически перебивает статус «Запланировано» на «Не выполнено» и портит данные при вводе задним числом. Здесь просроченность вычисляется на лету, статус хранимого поля не трогается.

### 3.4 Справочники

| Справочник | Значения |
|---|---|
| `crm.b2b_deal_sources` | почта info · тильда · почта head · телефон · кэррот · личная коммуникация с B2B-клиентом · личная коммуникация с B2C-клиентом · сложно указать источник |
| `crm.b2b_deal_statuses` | Новый запрос → В работе → Запрос снят → КП готовится → КП отправлено → Переговоры → **Продано** / **Неуспешно**. Поля: `order`, `is_final`, `is_success` |
| `crm.b2b_loss_reasons` | отказ клиент (причина неизвестна) · отказ клиент (слишком дорого) · отказ клиент (не сложились отношения) · отказ школа (не наш запрос) · отказ школа (не наш клиент по духу) · нет ответа от клиента · потеряли контакт (с нашей стороны) · иное |
| `crm.b2b_directions` | Игропрактики. Диагностика команды · Ресурс нефункционального · Кросс-командное взаимодействие · Управление стрессом · Эффективность в неопределенности · Управление командными отношениями · Стратегическая сессия · Индивидуальный коучинг · Hogan assessment · Harthill assessment · Программа под индивидуальный запрос |
| `crm.b2b_action_types` | звонок · сообщение в Telegram · письмо · встреча / зум · отправка КП · отправка программы · другое |

Справочники — таблицы, а не enum: список направлений и причин отказа будет пополняться, а enum в Озме меняется правкой метаданных.

### 3.5 Продукт — что добавляем

В `crm.actions` (существующая таблица, ничего не ломаем):

| Поле | Тип |
|---|---|
| `b2b_deal` | ref → `crm.b2b_deals` |
| `b2b_client` | ref → `crm.b2b_clients` — проставляется триггером из сделки, нужно для быстрых фильтров и для исторических продуктов без сделки |
| `b2b_product_type` | enum: пробное / знакомство · основная программа · стратегическая сессия · мероприятие · кастомная программа |
| `b2b_direction` | ref → `crm.b2b_directions` — одно основное направление |
| `b2b_audience` | enum: топ-команда · линейные сотрудники · смешанная команда |
| `kp_link` | string |
| `program_link` | string |

Направление на сделке — мультивыбор (что обсуждали), на продукте — одно (что купили). Это ровно граница «как продавали / что купил».

Формат, длительность, стоимость, договор и реализация уже есть в текущей форме продукта и в `reports.b2b_contracts` — не дублируем.

## 4. Логика

### 4.1 Триггеры

1. **Лог статусов** — при изменении `status` у сделки пишет строку в `b2b_deal_status_log` с датой и автором.
2. **Причина отказа обязательна** — запрещает сохранить сделку в финальном неуспешном статусе без `loss_reason`.
3. **Клиент в продукте** — при задании `b2b_deal` проставляет `b2b_client` из сделки.
4. **Дата закрытия** — при переходе в финальный статус ставит `closed_date`.
5. **Папка на Диске** — при первом переходе в «КП готовится», если папки нет, запускает её создание.

### 4.2 Действие «Создать продукт»

Кнопка на форме сделки. Создаёт `crm.actions` с `is_b2b = true`, `type = 'Продукт'` и переносит: организацию-заказчика и её название, ответственного менеджера, аудиторию, ссылку на КП, `b2b_deal`, `b2b_client`. Направление ставит автоматически, если у сделки выбрано ровно одно, иначе оставляет пустым. Название — из сделки с порядковым номером продукта.

Кнопку можно нажать несколько раз: одна сделка → много продуктов.

### 4.3 Яндекс.Диск

Проверено: Озма умеет делать внешние HTTP-запросы через `OzmaDB.enqueueHttpRequest` с колбэком на ответ — механизм уже используется для Telegram-напоминаний и касс. Внешний воркер не нужен.

Структура:

```
/B2B/{Клиент}/{ГГГГ-ММ} Сделка №{id} — {название}/
    ├── Запрос (интервью)      ← запись зума, расшифровка
    ├── КП
    ├── Программа
    └── Договор
```

API Яндекс.Диска не создаёт вложенные папки за один запрос, поэтому уровни создаются цепочкой запросов через колбэки. Код 409 («уже существует») считается успехом. После создания папка публикуется, ссылка записывается в `disk_folder`, статус — в `disk_folder_status`; при ошибке статус «ошибка» и текст в примечании, чтобы сбой был виден в интерфейсе, а не потерялся.

### 4.4 Точки для Telegram-агента

Агента делаем отдельно, здесь только готовим ему опоры: поле `tg_topic_id` на сделке (в каком топике чата писать), вью «Что горит» как источник напоминаний и вью-очередь событий, которые агент должен отписать в чат.

## 5. Интерфейс

| Вью | Содержание |
|---|---|
| `crm.b2b_clients_table` | Клиенты: имя, организации, ответственный, сделок всего / активных / выигранных, продуктов, последний контакт, дата следующего контакта. Фильтр по организации |
| `crm.b2b_client_form` | Карточка клиента: реквизиты, триггерные точки, блоки «Организации», «Контакты», «Сделки», «Продукты» — вся история отношений на одном экране |
| `crm.b2b_deals_table` | Воронка: сделки с группировкой по статусу и суммами |
| `crm.b2b_deal_form` | Карточка сделки: запрос клиента, наше понимание, источник, сумма, статус; блоки «Действия», «История статусов», «Продукты»; кнопки «Создать продукт» и «Создать папку на Диске» |
| `crm.b2b_organizations_coverage` | Охват по организациям: сколько клиентов, сделок, денег в одной компании |
| `crm.b2b_whats_hot` | «Что горит»: просроченные и сегодняшние действия, сделки без активности 14+ дней, наступившие даты следующего контакта и месяцы бюджетирования |
| `crm.b2b_products_table` | Существующая таблица продуктов + колонки клиент, сделка, тип, направление |

Плюс пункты меню, чтобы всё это открывалось из одного места — принцип единого входного окна из ТЗ.

## 6. Этапы

1. Справочники, клиент, организации клиента, контакты.
2. Сделки, лог статусов, действия.
3. Поля в продукте, действие «Создать продукт», триггеры.
4. Вью и меню.
5. Яндекс.Диск.
6. Точки подключения агента.
7. Миграция 20 существующих продуктов под клиентов и сделки — отдельным решением.

Промежуточных работающих состояний три: «клиент и сделка заводятся руками» → «продукт создаётся из сделки» → «видно, что горит».

## 7. Вне скоупа

Аналитика (воронка в деньгах, конверсии, скорость обработки, причины отказов, путь от первого продукта ко второму, прогноз бюджета) — в самом ТЗ обозначена следующим слоем и строится, когда накопятся данные. Разграничение прав ролями. Сам Telegram-агент.

## 8. Риски и открытые пункты

1. **Правка метаданных Озмы через MCP ненадёжна** — известно, что изменения user_views падают с пустой internal-ошибкой даже на no-op. Часть объектов, возможно, придётся заводить руками в интерфейсе Озмы. На оценку сроков влияет, на архитектуру — нет.
2. **Хранение OAuth-токена Яндекс.Диска в Озме** — нужно определить, где он лежит; способ выбираем на этапе 5, по образцу того, как уже хранится токен Telegram-бота.
3. **Аккаунт и корневая папка Диска** — принято по умолчанию: `bella.fatt@`, корень `/B2B`. Если материалы B2B лежат на другом аккаунте, меняем на этапе 5.
4. **Тип вью для воронки** — канбан-доска, если Озма его поддерживает; иначе таблица с группировкой по статусу. На данные не влияет.
5. **Названия клиентов** — при миграции 20 продуктов заказчики записаны неровно («Яндекс» в одном месте текстом, в другом ссылкой на организацию; два продукта называются «Новый B2B-продукт» и пустые). Чистка — часть этапа 7.

## Триггеры

| Триггер | Что делает | Проверено |
|---|---|---|
| `crm.b2b_write_deal_status_log` | пишет строку лога на каждую смену статуса | цепочка «— → Новый запрос → КП отправлено → Неуспешно» с автором |
| `crm.b2b_deal_close_check` | не даёт закрыть сделку в неуспех без причины отказа, ставит дату закрытия | отклонил закрытие без причины, пропустил с причиной, дата проставилась |
| `crm.b2b_sync_product_client` | проставляет продукту клиента из его сделки | клиент подставился при создании продукта |

Предыдущий статус берётся из последней записи лога, а не из старого значения строки: AFTER-триггер в Озме старое значение не отдаёт.

## Действие

`crm.create_b2b_product_from_deal` — создаёт продукт из сделки, переносит юрлицо, ответственного, аудиторию и направление (только если на сделке выбрано ровно одно), заводит те же 4 служебных занятия, что и старая кнопка создания B2B-продукта. Повторный запуск даёт второй продукт с номером в названии — проверено, получилось «Сделка» и «Сделка (2)».

Карточки: `b2b_client_form`, `b2b_deal_form`.
Блоки внутри карточек: `b2b_organizations_for_client`, `b2b_contacts_for_client`, `b2b_deals_for_client`, `b2b_products_for_client`, `b2b_directions_for_deal`, `b2b_actions_for_deal`, `b2b_status_log_for_deal`, `b2b_products_for_deal`.

Дополнены существующие: `b2b_products_table` (колонки клиент, сделка, тип, направление) и `b2b_product_form` (новые поля из ТЗ). В `user.main` добавлен раздел «Продажи B2B».

## Не сделано (осознанно)

2. **Миграция 20 существующих продуктов** под клиентов и сделки — по договорённости после того, как структуру посмотрят вживую.
3. **Аналитика** и разграничение ролей — вне скоупа.

## Замеченное при работе с Озмой

Запись метаданных через MCP иногда отвечает пустой internal-ошибкой или таймаутом, **уже применив изменение**. Один раз это привело к дублю блока в меню: вызов отчитался ошибкой валидации, но закоммитился. Правило на будущее: после любой ошибки на записи метаданных сначала проверять фактическое состояние (`list_entity_fields`, `get_user_view_query`), а не повторять вызов вслепую. Параллельные правки полей гоняются друг с другом — писать последовательно.

## Правки по итогам первого просмотра (03.09.2026, вечер)

**Меню.** Раздел «Продажи B2B» перенесён из второй позиции (между «Набор и продажи» и «Учебный процесс») на место перед «Абонементами» — вставка в начало сдвигала всю сетку и уводила «Учебный процесс» из его колонки.

Проставлено пятерым: Сучкова 11061, Вавилина 11362, Гусакова 15832, Ромашко 28, Старцев 29 — у первых трёх в базе есть однофамильцы-дубли, взяты те же записи, что уже стоят менеджерами в существующих B2B-продуктах. Поля «Ответственный аккаунт» (клиент) и «Ответственный» (сделка) подбирают значения через `crm.b2b_accounts_select`. Список пополняется галочкой, без правки кода.

**Бюджетирование.** Поле `budgeting_month` (int 1–12) заменено на `budgeting_period` (строка) — «октябрь 2026» пишется свободно. Подписи: «Когда согласуется бюджет (месяц, год)» и «Как согласуется бюджет (ответственные лица)».

**Раскладка карточки клиента.** Слева: клиент, команда, ответственный аккаунт, дата следующего контакта, папка на Диске, заметки. Справа: блок возвращения клиента (повод, что предложить дальше) и следом бюджетирование. Организации и Контакты стоят рядом в полширины, под ними Сделки, затем Продукты. Многострочными сделаны заметки, повод для возвращения, что предложить дальше, как согласуется бюджет, а в сделке — запрос клиента, наше понимание и заметки.

**Действия: остаются на сделке.** Заводятся и редактируются только внутри сделки — у действия всегда есть предмет разговора, а «действие по клиенту вообще» его теряет. На карточке клиента добавлен блок «Все действия по клиенту» (`crm.b2b_actions_for_client`) — сводка по всем сделкам, только для чтения, с переходом в сделку.

**Названия в ссылочных полях.** Таблицы показывали id вместо названий: в OzmaDB отображаемое значение задаётся не вычисляемым полем `main_name`, а колонкой `main_field` в `public.entities`. Проставлено: справочникам — `name`, клиенту и сделке — `main_name`, контактам — `full_name`.

**Тестовые данные оставлены в базе** для проверки интерфейса: клиент «Тест b2b — Команда маркетинга» с двумя контактами, две сделки («диагностика команды» — Продано, с привязанным продуктом `Новый B2B-продукт` id 12320; «управление стрессом» — Переговоры), четыре действия, одно из них просроченное. Организации к тестовому клиенту не привязаны намеренно — не хотелось цеплять реальное юрлицо из `base.organizations` к тестовой карточке.

## Правки по итогам второго просмотра (04.09.2026)

**Карточка клиента.** Контакты подняты наверх во всю ширину, организации под ними — контактов у клиента много, в полколонки они не помещались. Добавлен блок «Мастера, работавшие с клиентом»: тянется из `crm.masters_for_actions` по продуктам клиента, каждая строка подписана продуктом и сделкой.

**Статусы сделки.** Переименованы: «Продано» → «Успешная сделка», «Неуспешно» → «Неуспешная сделка». Цвет вынесен в поле `color` справочника `crm.b2b_deal_statuses`, вью красит ячейку через `cell_color = d.status=>color` — палитру можно менять данными, без правки вью. Новый запрос белый, В работе голубой, Запрос снят оранжевый, КП готовится и КП отправлено жёлтые, Успешная зелёная, Неуспешная красная. «Переговоры» в задании цвета не получили — поставлен лавандовый `#e1bee7`, чтобы последний шаг перед закрытием не путался ни с жёлтым, ни с зелёным.

**Причина отказа у успешной сделки.** В справочник добавлено значение «—», триггер `b2b_deal_close_check` проставляет его при переходе в успешный финальный статус: пустое поле читается как «забыли заполнить». Обратный переход из успешного в неуспешный прочерк не засчитывает за причину и по-прежнему требует настоящую.

**Справочники пополняются из выпадающего списка.** У аудитории и причины отказа заведены формы (`b2b_audience_form`, `b2b_loss_reason_form`) и подключены через `select_view … new: true` — новое значение добавляется прямо из карточки сделки. Ради этого `audience` перестала быть enum: и на сделке, и на продукте (`crm.actions.b2b_audience`) это теперь ссылка на справочник `crm.b2b_audiences`.

**Карточка сделки.** «Конкретный человек» из ссылки на всю базу людей превращён в текстовое поле `source_person_text` — выбор из десятков тысяч карточек CRM был неудобен. Рядом добавлено `source_note` («Как именно к нам пришли») для истории появления запроса. Сумма и даты в таблицах сузились и получили денежный формат (`number_format = 'ru'`, `column_width`). Блок направлений запроса переехал в один раздел с полем «Наше понимание запроса (плюс что мы предлагаем клиенту)» и стоит прямо над ним. Материалы стали многострочными.

**Папки на Диске.** Поле папки и статус папки убраны из сделки. Папок две, а не три: большая по клиенту (`crm.b2b_clients.disk_folder`) и по конкретному продукту (`crm.actions.b2b_disk_folder`, добавлено). У неуспешной сделки папка не нужна вовсе, у успешной материалы живут в папке продукта. `disk_folder_status` удалён — состояние создания папки в интерфейсе не нужно.

**Действия.** Колонка-галочка «Просрочено» убрана из вью (само поле `is_overdue` осталось для будущих фильтров и агента). Вместо неё красится дата: просроченное запланированное — красным, будущее — зелёным. Выполненные действия красятся целиком серым. При создании действия внутри сделки ответственный подставляется сам — из ответственного по сделке, а если он не задан, из аккаунта клиента.

## Правки по итогам третьего просмотра (04.09.2026)

**Ширины колонок.** Счётчикам, датам и суммам во всех таблицах B2B проставлен `column_width` — по умолчанию Озма растягивает колонку «Сделок» на треть экрана.

**Порядок в меню:** Клиенты → Сделки → Продукты B2B → К кому вернуться → Что горит → Охват по компаниям.

**Организации уехали в самый низ карточки клиента** и сжаты до трёх колонок (организация, основная, ИНН). Это справочная информация, наверху она занимала место, нужное контактам. Порядок карточки: поля клиента и возвращение/бюджет → Контакты → Сделки → Продукты → Мастера → Все действия → Организации.

**Цвет статуса: атрибуты не понимают `=>`.** `cell_color = d.status=>color` молча не работает, хотя в теле запроса та же цепочка отдаёт значение. Лечится вычисляемым полем: `crm.b2b_deals.status_color = status=>color`, `crm.b2b_deal_actions.deal_status_color = deal=>status=>color`, а вью красит по нему. Цвета остаются данными справочника.

**Продукт разгружен.** Поле «Клиент» скрыто с формы (проставляется триггером из сделки, на экране дублировало сделку), ссылки на КП, программу и папку Диска перенесены из средней колонки в правую, к деньгам и договору. Всего в продукт добавлено 8 полей: сделка, клиент (скрытое), тип продукта, направление, аудитория, КП, программа, папка на Диске.

**Ограничение.** `number_format = 'ru'` красиво разделяет разряды в таблицах, но в самой карточке сумма — редактируемое поле ввода, там разделители не показываются. Это поведение Озмы, не настройка вью.
