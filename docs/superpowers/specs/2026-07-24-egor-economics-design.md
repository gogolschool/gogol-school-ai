## Механика economics ↔ P&L (из разбора кода)

- Каждая строка `fin.pl_report_final` ссылается на исходную запись через `external_transaction = fin.economics.id` и зеркалит её классификацию: `category`, `project`, `expenditure_type`, `segment`, `referenced_employee`, `marketing`, `pl_date`.
- Категория P&L — **производная** (`getCategoryForPLTransaction` в модуле `pl_report.mjs`): выводится из `expenditure_type + segment + project + marketing`; на `economics` не хранится.
- `pl_date = economics.start_date` (не `transaction_date`).
- Триггер `fin.update_pl_after_amount_changing` пересобирает строку P&L (delete + regenerate). **Ловушка**: реагирует на изменение `amount`; правка одной только классификации может НЕ пересобрать строку (память `reference_pl_date_source`). → Егор после записи обязательно проверяет `pl_report_final` и при необходимости правит строку напрямую / форсит пересборку.
- `split_parts` имеет валидатор `validate_split_parts_for_economics` — сумма долей должна биться.

## Поток скилла

1. Очередь: `SELECT … FROM fin.economics WHERE additional_comment IS NOT NULL AND additional_comment <> ''`. Группировка по типу флага, крупнейшие суммы вперёд.
2. Разбор записи: парсинг флага + дорасследование по фактам (текст платежа, справочники Озмы, правила разнесения) → предложение `project`/`expenditure_type`/`segment`/`marketing`/`referenced_employee`/дат/`split_parts`.
3. Решение по P&L: итоговая категория/проект/месяц, «было → станет».
4. Подтверждение: да / правка / пропустить.
5. Запись (после «да»): `mcp__ozma__transaction` — правка полей; гашение флага (`additional_comment = 'проверено Егор ДД.ММ.ГГГГ'`, при уместности `is_transaction_checked=true`); проверка `pl_report_final` по `external_transaction`, при необходимости — прямая правка строки P&L.
6. Сводка: разобрано / записано / эскалировано / осталось флагов.
